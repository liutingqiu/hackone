# 部门链路（流水线 + 回退）

> 2026-11-07 11:45 · 主控设计
> 解决两个问题：部门之间不要只靠主控传话而丢失上下文；卡点要能打回上一环，而不是一路带病往下走。

---

## 一、先说清一个物理限制

**子 agent 之间没有直接通信通道。** DSH 的子 agent 只能与主控收发消息，不能互相 send_message。

所以**物理拓扑必然是星型**（都以主控为中心），但**逻辑拓扑可以是流水线**：

- 主控不转发"对话"，只转发**交接件**（结构化文档）
- 每个环只读上一环写下的文件，不需要知道上一环是谁、说了什么
- 主控在每一环做**闸门**（验收后才放行），而不是做传声筒

这样即使我一次只跟一个部门说话，信息也不会丢——因为它写在文件里。

## 二、链路

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   调研 research ──结论──▶ 开发 dev ──实现──▶ 测试 qa ──通过──▶ 运维 ops ──上线──▶ 用户测试 user-test
        ▲                   ▲   │                 │                  │                  │
        │                   │   └──── 打回 ────────┘                  │                  │
        │                   │        （P0 缺陷 / 逻辑错）              │                  │
        │                   └──────────── 打回 ────────────────────────┘                  │
        │                            （构建失败 / 体积超预算）                             │
        └──────────────────────────── 打回 ─────────────────────────────────────────────┘
                                     （用户看不懂 / 不愿意用）
```

三条回退通道：

| 触发 | 打回到 | 判据 |
| --- | --- | --- |
| 代码缺陷、逻辑错 | 开发 | 测试部 P0 用例失败，附复现路径 |
| 构建失败、体积超预算、部署不可用 | 开发 | 运维在 CI 或部署阶段拦截 |
| 用户看不懂、卡住、不愿意用 | 开发（必要时联合调研） | 用户测试的「会让用户放弃」清单 |

**不允许跨级打回**：运维不能直接打回调研，用户测试不能直接改代码——它们只能打回到上一环，由上一环决定要不要再往上打回。

## 三、交接契约（每环必须写）

每次交接产出一个文件，放在 `docs/pipeline/handoff/<任务ID>-<环节>.md`，四段缺一不可：

```markdown
## 输入
（我依据的上游产物路径）

## 产物
（本次交付的文件路径 / URL）

## 验收标准
（下家拿什么判我合格，必须可执行）

## 证据
（截图 / 测试输出 / CI run id / journal 行）

## 下家
research | dev | qa | ops | user-test | done
```

**没有交接文件 = 没有交接。** 口头说"做完了"不算。

## 四、看板（单一事实源）

`docs/pipeline/BOARD.md`，一行一个任务，状态只有六种：

`待调研 → 待开发 → 待测试 → 待上线 → 待体验 → 完成`（外加 `打回`）

主控每次推送后更新。任何人都能一眼看出：现在卡在哪一环、卡了多久。

## 五、闸门规则（主控怎么放行）

| 闸门 | 放行条件 | 不放行怎么办 |
| --- | --- | --- |
| 调研 → 开发 | 结论有来源链接或实测记录；有明确的"做什么" | 打回补证据 |
| 开发 → 测试 | CI 五道关全绿；有单测；体积在预算内 | 打回开发 |
| 测试 → 运维 | P0 用例全绿；无阻塞缺陷 | 打回开发，附复现 |
| 运维 → 用户测试 | 线上可访问；构建可复现 | 打回开发或运维 |
| 用户测试 → 完成 | 无「会让用户放弃」级卡点 | 打回开发 |

## 六、时间盒与升级

| 环节 | 时间盒 | 超时处理 |
| --- | --- | --- |
| 调研 | 40 min | 结论不全也要交，标「未验证」 |
| 开发 | 90 min / 棒 | 拆小，交可用的部分 |
| 测试 | 45 min | 先交 P0 结论 |
| 运维 | 15 min | 失败即回滚，留 runbook |

**同一任务被打回第二次，升级到主控裁决**——不许两个部门来回踢皮球。

## 七、并行规则

- 调研可以**边做边给**开发（先给一条确定的，不等全做完）
- 运维的准备（配置、runbook）不等代码
- 用户测试可以在**每次部署后立刻跑**，不必等全部功能完成

串行只是为了验收，执行可以并行。

## 八、为什么这样设计

如果全走主控口头转发：
- 上下文在转发中丢失（我只能转述，不能搬原文）
- 每个部门都要等我，我成了吞吐瓶颈
- 出问题找不到是哪一环的责任

改成交接件 + 看板后：
- 信息在文件里，无损
- 我可以同时推进多条线（准备、开发、体验互不等待）
- 每一环的输入输出可追溯，评委问"这是谁做的、依据什么"，直接指文件
