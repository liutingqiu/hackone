## ADR-001 前端技术栈

**状态**：提案

**背景**：队友的实现是「Python 模板 + 单文件 HTML」（纯原生 JS、零依赖、双击可用）。它在离线演示上极稳，但作为要长期上线的产品有三个问题：无模块化、无类型约束、无构建生态（打包、分包、压缩、缓存策略都靠手工）。

**决策**：主实现用 **Vite + React + TypeScript + Canvas 2D**。单文件 HTML 版本保留为参考实现与离线兜底。

**理由**：
- Vite 的构建产物天然适合静态托管（Pages），按需分包、长期缓存
- TypeScript 在多人协作与后期维护上是硬需求
- React 的组件化便于「专业/小白」两种界面共用逻辑

**性能约束（写死，评审时按这个卡）**：

| 指标 | 预算 |
| --- | --- |
| 首屏 JS（gzip） | < 150 KB |
| 首屏可交互（本地网络） | < 1.5 s |
| 400×400 图纸重绘 | < 16 ms（一帧） |
| 图片量化（200×200 格） | < 300 ms，且不阻塞主线程 |

**手段**：量化和最近色匹配放 Web Worker；画布分块渲染 + 视口裁剪；色板按需加载（小白模式只打包 MARD 291）；不做全局状态库。

**代价**：需要 Node 构建链路；单文件离线版与主版本会分叉，需明确「主版本为准，离线版只做演示兜底」。

## ADR-002 部署形态

**状态**：提案

**决策**：**Cloudflare Pages 静态托管**，绑定 `liutingqiu.xyz` 的子域（如 `hack.liutingqiu.xyz`）。腾讯云服务器暂不启用，留作后续需要服务端能力时使用。

**理由**：
- 产品是纯前端计算（图片不上传），不需要服务端
- Pages 全球 CDN、免费、支持自定义域名与自动 HTTPS
- 国内服务器绑域名涉及备案，两天内不可控

**代价**：无服务端 = 无账号、无云端保存、无分享。若后续要做「图纸分享」，再启用腾讯云。

## ADR-003 色板数据来源

**状态**：**已接受**（YG 2026-11-07 定）

**决策**：只引入 **MIT 授权**的数据源：`HansBug/pindou-color-data`（主）与 `Jett-Wu/Perler_Beads_Generator`（校验）。禁用 Zippland（AGPL/自定义）、Pindo（GPL-3.0）、bitbead（无授权）。

**理由**：正式产品要商业化，GPL/AGPL 传染性与无授权数据都会在后期变成硬约束。

**代价**：放弃 Zippland 的 5 品牌映射覆盖度，跨品牌映射要自己算。

详见 [palette-sources.md](./palette-sources.md)。

## ADR-004 双模式架构

**状态**：提案

**决策**：产品分「小白模式（默认）」与「专业模式」，**同一代码库、同一套算法**，差异只体现在：默认参数、暴露的控件、界面密度、按需加载的色板范围。

**理由**：
- 目标用户两极分化：手工圈新手要「传图就能拼」，进阶玩家要「色号体系、算法、跨品牌替换」
- 两套代码会让维护成本翻倍，且 48 小时内做不完

**约束**：
- 模式切换不改数据结构，图纸在两模式间可无损切换
- 小白模式首屏不加载专业模式的色板与算法 chunk
- 「分板」在两种模式下都默认开启（这是差异化卖点，不能藏在专业模式里）

## ADR-005 团队协作与代码归属

**状态**：提案

**决策**：以 YG 侧为主线代码来源；队友的实现作为**参考实现**（算法思路、色板加工流程可借鉴），不直接合并其文件。队友接受协作后按其分支提交，走 PR 评审。

**理由**：队友目前通过 GitHub 网页上传整份文件，没有本地仓库，与他并行修改同一份文件必然冲突。

**待办**：让队友 clone 仓库、装 Node、走分支；或明确他只在独立目录（如 `reference/`）提交。
