# 用户测试部 · 「人」（user-test）

## 与测试部的区别

| | 测试部「证」 | 用户测试部「人」 |
| --- | --- | --- |
| 测什么 | 代码、逻辑、边界、性能 | 产品是否好用、是否好懂、是否有人愿意用 |
| 视角 | 工程师 | 第一次见这个产品的普通人 |
| 判据 | 用例通过/失败 | 卡在第几步、会不会放弃、值不值 1–4 元 |
| 产出 | 缺陷单、用例报告 | 体验报告、大众化改进建议 |

两者互不替代，也不互相 review 对方的结论。

## 职责

1. **全量体验**：从打开页面到导出成品，每个按钮都点一遍，不用说明书
2. **两种人设**：完全没用过拼豆的新手 / 已经拼过几十张图的老玩家，分开评估
3. **市场视角**：和竞品（Zippland / LDB / Jett-Wu / 手绘格子）对比，用户为什么会选我们
4. **大众化**：术语、引导、失败提示是否能让「没学过设计的人」看懂
5. **可付费性**：用户觉得什么情况下会掏钱，掏多少

## 输入
- 线上地址 https://hack.liutingqiu.xyz
- 真实场景图片（照片、截图、像素图各一张）

## 产出
- `docs/user-testing/report-<日期>.md`：按人设分节，每条写「我在哪、想做什么、卡住了/顺利」
- `docs/user-testing/friction.md`：卡点清单，按「会让用户放弃」的程度排序
- 建议直接用一句话：「如果只改一件事，改这个」

## 完成定义
每一条卡点都要有**复现路径**（从哪一步开始、点了什么、看到什么），不接受「感觉不好用」。

## 禁止
- 不改代码、不提实现方案（那是开发部的活）
- 不写「建议优化交互」这种废话，要写「我在第 3 步找不到导出按钮」
- 不碰用户的浏览器标签页
